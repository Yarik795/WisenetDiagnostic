# Требования к веб-интерфейсу — Wisenet Диагностика

> **Статус:** черновик на согласование  
> **Версия:** 0.2  
> **Дата:** 2026-05-20  
> **Связанные документы:** [BUSINESS_REQUIREMENTS.md](./BUSINESS_REQUIREMENTS.md)

Документ задаёт визуальный язык, UX и состав экранов для веб-UI на **Jinja2 + HTMX** (серверный рендер, без Node.js). Бизнес-логика и этапы развития — в бизнес-требованиях.

---

## 1. Цели интерфейса

| Цель | Описание |
|------|----------|
| **Оперативность** | За 3–5 секунд понять, есть ли проблемы на объекте |
| **Иерархия** | Объект важнее регистратора: сначала объект, внутри — NVR |
| **Современность** | Тёмная тема уровня продуктов мониторинга (Grafana, Datadog, Linear) |
| **Масштаб** | Удобная работа со списком из сотен объектов и тысяч устройств (поиск, фильтры, группировка) |
| **Расширяемость** | Заложить место под статусы «светофор», каналы, дашборды без смены каркаса |

---

## 2. Визуальный стиль: тёмная тема

### 2.1. Общее направление

- **Только тёмная тема** на этапах 0–1 (переключатель light/dark — не обязателен).
- Стиль: **минималистичный, «панель мониторинга»**, без декоративного «киберпанка».
- Акценты сдержанные; яркий цвет — для статусов и primary-действий.
- Поверхности с лёгкой глубиной (слои фона + тонкая обводка), без тяжёлых теней.

### 2.2. Цветовая палитра (рекомендуемые токены)

| Токен | Назначение | Пример (HEX) |
|-------|------------|--------------|
| `bg-base` | Фон приложения | `#0B0E14` |
| `bg-surface` | Карточки, панели | `#12161F` |
| `bg-elevated` | Модалки, dropdown, hover-ряд | `#1A2030` |
| `border-subtle` | Разделители, обводки | `#2A3348` |
| `text-primary` | Основной текст | `#E8ECF4` |
| `text-secondary` | Подписи, метаданные | `#8B95A8` |
| `text-muted` | Плейсхолдеры, disabled | `#5C6678` |
| `accent` | Primary-кнопки, фокус, ссылки | `#3B82F6` |
| `accent-hover` | Hover primary | `#2563EB` |
| `status-ok` | Исправно / online | `#22C55E` |
| `status-warn` | Деградация | `#EAB308` |
| `status-error` | Неисправно / offline | `#EF4444` |
| `status-unknown` | Нет данных | `#6B7280` |

Допустимо уточнить оттенки при вёрстке; важно сохранить **контраст WCAG AA** для текста на фоне.

### 2.3. Типографика

| Элемент | Шрифт | Размер / начертание |
|---------|-------|---------------------|
| UI | **Inter** или **Geist** (system-ui fallback) | — |
| Моноширинный (IP, порты, ID) | **JetBrains Mono** / **IBM Plex Mono** | 13–14px |
| H1 (заголовок страницы) | Inter | 24px, semibold |
| H2 (секция / объект) | Inter | 18px, semibold |
| Body | Inter | 14px, regular |
| Caption | Inter | 12px, medium, `text-secondary` |

Межстрочный интервал: 1.4–1.5 для таблиц и форм.

### 2.4. Скругления, отступы, сетка

- Радиус карточек и инпутов: **8px** (кнопки — 6–8px).
- Базовый шаг отступов: **4px** (4, 8, 12, 16, 24, 32).
- Контентная зона: max-width **1440px**, на широких экранах — по центру с боковыми полями.
- Минимальная зона клика для кнопок и иконок: **40×40px**.

### 2.5. Иконки и иллюстрации

- Набор: **inline SVG** (иконки Lucide-стиля, stroke 1.5–2px) в шаблонах или `/static`.
- Пустые состояния: простая иконка + текст, без стоковых иллюстраций.
- Логотип/название продукта в sidebar: «Wisenet Диагностика» или сокращённо «WD».

## 3. Компонентная база (технические ориентиры)

| Решение | Требование |
|---------|------------|
| Шаблоны | **Jinja2** (`backend/app/templates/`) |
| Интерактив | **HTMX** (CDN): частичные обновления строк, формы, redirect после сохранения |
| Стили | Один **`app.css`** с CSS-переменными палитры (п. 2.2), без сборки npm |
| Таблицы | Сортировка, sticky header; виртуализация при >100 строк (этап 1+) |
| Формы | POST + валидация на сервере, ошибки inline в шаблоне |
| Уведомления | Toast через `HX-Trigger` / query после redirect |
| Подтверждения | `hx-confirm` на удаление |
| Загрузка | Skeleton (CSS); `htmx-indicator` / spinner на «Проверить» |
| Клиентский JS | Минимальный `app.js`: свёртка групп (`localStorage`), поиск по списку |

Анимации: **короткие** (150–200ms), `prefers-reduced-motion` — отключать переходы.

> На этапах с дашбордами и «светофором» допустим отдельный SPA (React/Vue); этап 0 — без npm.

## 4. Каркас приложения (layout)

### 4.1. Структура

```
┌─────────────────────────────────────────────────────────────┐
│  Sidebar (240px)  │  Header (breadcrumb + actions)        │
│                   ├───────────────────────────────────────┤
│  • Объекты        │                                       │
│  • Регистраторы   │  Main content                         │
│  • Настройки*     │                                       │
│                   │                                       │
└─────────────────────────────────────────────────────────────┘
* Настройки — учётные данные API (этап 0)
```

- **Sidebar** — тёмнее `bg-surface`, фиксирован слева; на узком экране (<1024px) — drawer по гамбургеру.
- **Header** — заголовок текущей страницы, глобальный поиск (этап 1+), кнопка «Добавить регистратор».
- **Main** — скролл только в контенте, sidebar и header фиксированы.

### 4.2. Навигация

**Инвентарь**

| Пункт | Маршрут | Назначение |
|-------|---------|------------|
| Объекты | `/objects` | Реестр NVR: вид по объектам (по умолчанию) или таблица (`?view=table`) |

**Мониторинг**

| Пункт | Маршрут | Назначение |
|-------|---------|------------|
| Сводка | `/status` | Дашборды по категориям здоровья (время, HDD, каналы и др.) |
| Каналы | `/channels` | Детализация по каждой камере |
| История | `/history` | Журнал смены статусов |

**Прочее:** Настройки (`/settings`) — учётные данные API.

Совместимость: `/recorders` → редирект на `/objects?view=table`; `/time` → `/status?category=time`.

Основной сценарий инвентаря — **«Объекты»**; табличный вид — переключатель на той же странице.

## 5. Иерархия в UI: Объект → Регистратор

### 5.1. Модель отображения

- **Объект** — логическая точка эксплуатации (отделение, ВСП, офис). Идентифицируется **названием** (`object_name`), вводится при создании регистратора.
- **Регистратор** — всегда принадлежит ровно одному объекту (поле обязательное).
- На одном объекте может быть **несколько** регистраторов.

Целевая иерархия на будущее (заложить в навигации и breadcrumb):

`Регион → Город → Объект → Регистратор → Канал`

На этапе 0 в UI и конфиге реализуется уровень: **Объект → Регистратор**.

### 5.2. Экран «Объекты» (главный)

**Вид по умолчанию:** сгруппированные карточки или аккордеон.

```
▼ Отделение №12 — г. Москва          [ 2 NVR ]  ● 1 offline
    ├─ NVR-1  10.1.2.3:80    ● Online     [Проверить] [⋯]
    └─ NVR-2  10.1.2.4:80    ● Offline    [Проверить] [⋯]

▼ ВСП-045 — Казань                   [ 1 NVR ]  ● Online
    └─ NVR-main  ...
```

Требования:

| ID | Требование |
|----|------------|
| UI-01 | Группировка строго по `object_name` |
| UI-02 | В заголовке группы: название объекта, счётчик NVR, агрегированный статус (худший из дочерних: error > warn > ok > unknown) |
| UI-03 | Группы сворачиваются/разворачиваются; состояние свёрнутости — в `localStorage` |
| UI-04 | Поиск по названию объекта, имени/IP регистратора — фильтрует список без перезагрузки |
| UI-05 | Сортировка объектов: по имени (А–Я), по статусу (проблемные сверху) |

### 5.3. Экран «Регистраторы» (плоский)

- Таблица: Объект | Имя NVR | Host | Порт | Статус | Последняя проверка | Действия.
- Те же действия, что в группированном виде.
- Клик по названию объекта — переход на `/objects` с раскрытой группой (deep link: `?object=...`).

## 6. Формы и действия (этап 0)

### 6.1. Добавление / редактирование регистратора

Открывается **drawer справа** (ширина ~480px) или модальное окно — предпочтительно **drawer** для длинных форм.

| Поле | Обязательность | Подсказка |
|------|----------------|-----------|
| **Название объекта** | Да | «Отделение №12», «ВСП-045» — как в эксплуатации |
| Имя регистратора | Нет (если пусто — показывать host) | «NVR-1», «DVR цоколь» |
| Host (IP/DNS) | Да | Валидация формата |
| Порт | Да | По умолчанию 80 |
| HTTPS | Нет | Toggle |
| Включён | Да | Toggle, по умолчанию вкл. |

Кнопки: **Сохранить** (primary), **Отмена** (ghost).

- При вводе `object_name`, совпадающем с существующим объектом, новый NVR **попадает в ту же группу** (без отдельного справочника объектов на этапе 0).
- Под полем «Название объекта» — autocomplete по уже существующим названиям (опционально, Should).

### 6.2. Проверка связи

- Кнопка **«Проверить»** на строке регистратора и в drawer.
- Во время проверки: disabled + spinner на кнопке.
- Результат: badge + время (`14:32:05`) + tooltip с текстом ошибки API.
- Не перезагружать всю страницу — обновить только строку/карточку.

### 6.3. Удаление

- Confirm dialog: «Удалить регистратор NVR-1 на объекте Отделение №12?»
- Объект как группа **исчезает**, если удалён последний регистратор.

### 6.4. Настройки (credentials)

- Отдельная страница `/settings`.
- Поля: логин, пароль (masked), кнопка «Сохранить».
- Предупреждение: «Пароль хранится в локальном config.json на сервере».

## 7. Статусы и индикаторы

### 7.1. Badge статуса

| Статус | Цвет | Текст в UI |
|--------|------|------------|
| Online | `status-ok` + мягкий фон 10% opacity | «Доступен» |
| Offline | `status-error` | «Недоступен» |
| Checking | `accent` + pulse | «Проверка…» |
| Unknown | `status-unknown` | «Не проверялся» |
| Disabled | `text-muted` | «Выключен» |

- Индикатор: **точка 8px** + текст или только точка в компактной таблице с tooltip.

### 7.2. Агрегат по объекту

| Правило | Отображение |
|---------|-------------|
| Все NVR online | Зелёная точка у заголовка объекта |
| Хотя бы один offline | Красная точка + badge «1 из 2 недоступен» |
| Есть unknown, нет offline | Серый/жёлтый по политике (по умолчанию — серый «не проверялся») |
| Все disabled | «Выключен» без цветового аларма |

## 8. Состояния интерфейса

| Состояние | Поведение |
|-----------|-----------|
| Загрузка списка | Skeleton: 3–5 строк групп |
| Пустой список | Центр: иконка + «Нет регистраторов» + CTA «Добавить регистратор» |
| Ошибка API | Banner вверху main: «Не удалось загрузить данные» + «Повторить» |
| Ошибка сохранения | Toast error с текстом от бэкенда |
| Успех сохранения | Toast success |

---

## 9. Адаптивность

| Breakpoint | Поведение |
|------------|-----------|
| ≥1280px | Sidebar постоянный, таблица полная |
| 1024–1279px | Sidebar узкий (только иконки) или collapsible |
| <1024px | Sidebar в drawer; таблица → карточки регистраторов; drawer формы на всю ширину |

Минимальная поддерживаемая ширина: **360px** (мобильный просмотр — вторичный, но форма должна быть usable).

## 12. Критерии приёмки UI (этап 0)

1. Веб-UI на `:8000` отображается **только в тёмной теме**, визуально цельное (палитра из п. 2).
2. Регистраторы сгруппированы по **названию объекта**; объект задаётся в форме добавления.
3. Работают: добавление, редактирование, удаление, проверка связи без полной перезагрузки страницы.
4. Есть экран настроек credentials и альтернативный плоский список регистраторов.
5. Пустые, загрузка и ошибка API обработаны по п. 8.
6. Интерфейс читаем на Full HD и при ширине 1024px.
