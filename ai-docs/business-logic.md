# Бизнес-логика Wisenet Диагностика

Платформа проактивного контроля исправности видеонаблюдения на оборудовании Hanwha Wisenet. Текущая версия (0.3.0) реализует этап 1: учёт регистраторов, автоматический опрос по SUNAPI, оценка здоровья NVR и каналов, дашборды и отчёты. ML-аналитика, SNMP, SLA-отчёты и интеграции с тикет-системами — вне текущего scope.

---

## Продукт и проблема

**Проблема.** В эксплуатации — крупный парк видеонаблюдения (порядка 4000+ камер). Неисправности (сеть, запись, потеря видео, сбой дисков, расхождение времени) часто обнаруживаются поздно — при расследовании инцидента или по жалобе, а не до наступления последствий.

**Решение.** Единая внутренняя платформа, которая:

- ведёт централизованный реестр регистраторов с привязкой к объектам эксплуатации;
- периодически опрашивает устройства через прикладной API (SUNAPI), а не только проверяет сеть;
- классифицирует состояние по понятным категориям и показывает «светофор» для операторов;
- сохраняет историю для последующей отчётности.

**Принцип развития:** сначала платформа и базовый мониторинг, затем качество видео, инфраструктура, SLA и автоматизация — без пересборки основы.

---

## Целевая аудитория

| Роль | Задача, которую решает продукт |
|------|--------------------------------|
| Эксплуатация / ТСО | Быстро видеть, что «лежит»; меньше ручного обхода NVR |
| Служба безопасности | Контроль исправности записи в критичных зонах |
| Руководство | Агрегированная картина по объектам (процент проблем, тренды — на следующих этапах) |
| Инженеры / подрядчик | Группировка инцидентов по объекту, а не тысячи отдельных точек |
| Разработка / владелец | Расширяемая платформа с единым конфигом и единым API опроса |

Доступ к веб-интерфейсу предполагается из доверенной внутренней сети; аутентификация пользователей на текущем этапе не реализована.

## Предметная область

### Иерархия учёта

```
Объект (object_name) → 1..N Регистраторов (NVR/DVR) → Каналы/камеры
```

- **Объект** — логическая точка эксплуатации (отделение, ВСП, офис). Задаётся текстовым полем `object_name` при добавлении регистратора; отдельного справочника объектов нет.
- **Регистратор** — NVR/DVR Wisenet с IP, портом, флагом HTTPS и признаком `enabled`.
- **Канал** — камера на регистраторе; список получается автоматически при инвентаризации (опрос `cameraregister` + `videosource`).

Целевая иерархия для отчётности на следующих этапах: Регион → Город → Объект → Регистратор → Канал.

### Источники данных

| Источник | Содержимое | Назначение |
|----------|------------|------------|
| `config.json` | Учётные данные API, список регистраторов, пороги мониторинга, `last_status` | Персистентная конфигурация; изменяется из UI и скриптов |
| SQLite (`data/monitoring.db`) | Каналы, метрики регистраторов, история статусов | Оперативные результаты опросов |
| CMDB (`cmdb.xlsx`) | IP, адрес, модель, MAC, функциональный тип, производитель | Справочник в SQLite `cmdb_records`; устройства ТСВ/СКУД/Био — также в `config.json` через `/sources` или `scripts/sync_config_from_cmdb.py` |

Для всех устройств используется **одна учётная запись** API (логин/пароль в конфиге).

## Модель исправности

Четыре состояния здоровья (`HealthStatus`):

| Состояние | Бизнес-смысл |
|-----------|--------------|
| **Исправно** (`ok`) | Устройство доступно, метрики в норме |
| **Деградация** (`warn`) | Работает, но есть риск (мало архива, предупреждение по температуре, часть каналов с проблемами ниже порога) |
| **Неисправно** (`error`) | Критичный отказ: NVR недоступен, потеря видео, сбой диска, критичное расхождение времени, архив ниже критического порога |
| **Неизвестно** (`unknown`) | Нет данных опроса, канал деактивирован, регистратор выключен в конфиге |

**Агрегация:** статус объекта и регистратора определяется по **наихудшему** статусу среди дочерних элементов. Сортировка в UI также отдаёт приоритет проблемным объектам.

Для связи (доступность API) отдельно хранится `CheckStatus`: online / offline / unknown / disabled. После полного опроса основным индикатором в UI становится `health_status` из БД.

## Категории мониторинга

Система оценивает восемь категорий; каждая классифицируется независимо и отображается бейджами на дашбордах:

| Категория | Что проверяется | Источник SUNAPI |
|-----------|-----------------|-----------------|
| Время / NTP | Расхождение с сервером, статус NTP, режим синхронизации | `system.cgi` → `date` |
| Доступность (SUNAPI) | Ответ HTTP/SUNAPI при опросе NVR | результат опроса |
| Температура HDD | Максимальная температура дисков | `storageinfo` + доп. запросы по модели |
| Накопители | Статус массива, статусы слотов, события HDDFail/HDDError | `storageinfo`, `eventstatus` |
| Вентиляторы | CPUFanError, FrameFanError и др. | `eventstatus` (системные события) |
| Аппаратные события | Прочие системные события (BatteryFail, MemoryError и др.), не отнесённые к дискам и вентиляторам | `eventstatus` |
| Каналы | Потеря видео, отключение камеры, статус регистрации, состояние источника | `cameraregister`, `videosource`, `eventstatus` |
| Глубина архива | Минимальная глубина записи по каналам vs норматив | `searchrecordingperiod` |

Пороги задаются в секции `monitoring` конфига (значения по умолчанию):

- интервал короткого опроса — 5 мин, полного — 15 мин;
- требуемая глубина архива — 30 сут.; критический порог — 7 сут.;
- расхождение времени: предупреждение ≥ 60 с, ошибка ≥ 300 с;
- температура HDD: предупреждение ≥ 50 °C, ошибка ≥ 60 °C;
- доля неисправных каналов для статуса «ошибка» регистратора — ≥ 25%;
- NTP-сервер и POSIX-часовой пояс для массового включения NTP.

## Правила оценки здоровья

### Канал

Оценка выполняется в `evaluate_channel_health` при каждом опросе:

1. `deactive` → неизвестно (канал не используется).
2. `off`, скрытый режим (`covert1`/`covert2`) → деградация.
3. VideoLoss или камера не подключена → неисправно.
4. Ошибка статуса регистрации камеры на NVR → неисправно; прочие не-OK статусы → деградация.
5. Канал включён и камера видна → исправно.

### Регистратор

Оценка в `evaluate_recorder_health` — наихудшее из:

- недоступность NVR (HTTP/SUNAPI);
- системные события (перегрузка CPU, сбои вентиляторов, ошибки HDD);
- статус и температура накопителей;
- NTP Fail, расхождение времени выше порогов;
- глубина архива ниже критического или требуемого порога;
- агрегированное состояние каналов (есть неисправные / есть деградация).

При полном опросе с инвентаризацией каналы, исчезнувшие с устройства, удаляются из БД.

### Категория «Каналы» на дашборде

Отличается от поштучной оценки: если доля каналов в `error` ≥ `channels_error_threshold_percent`, вся категория помечается как ошибка; иначе наличие единичных ошибок — деградация.

## Циклы опроса и действия пользователя

### Автоматический режим

Фоновый планировщик (`MonitoringScheduler`) при старте приложения **не опрашивает устройства**, пока пользователь не включит **Автообновление** в шапке страниц мониторинга (Сводка, ТСВ, СКУД, Биотерминалы). Состояние тумблера хранится в памяти процесса до перезапуска.

После включения автообновления:

1. **Короткий опрос** — каждые `poll_interval_minutes`: доступность, события, диски, время, архив; без обновления списка каналов.
2. **Полный опрос** — каждые `full_poll_interval_minutes`: то же + инвентаризация каналов и детальный архив по каналам.
3. **Суточная инвентаризация** — раз в 24 ч принудительный опрос с `include_inventory=True`.

Параллелизм ограничен `max_concurrent_polls` (по умолчанию 5), чтобы не перегружать SUNAPI.

### Ручные действия (UI)

| Действие | Эффект |
|----------|--------|
| Проверить регистратор | Полный опрос одного NVR |
| Опросить все устройства / Инвентаризация всех | Фоновая задача с прогрессом в UI (NVR + ping-устройства) |
| Автообновление (тумблер) | Вкл/выкл плановый опрос по расписанию |
| Экспорт отчёта / отправка на почту | Доступны в шапке всех страниц мониторинга |
| Включить NTP (один / все) | Запись NTP-настроек на устройство, повторный опрос; «все» — только для онлайн-NVR с проблемами времени |
| CRUD регистраторов | Запись в `config.json` |
| Настройки | Учётные данные и пороги мониторинга |
| Экспорт отчёта об ошибках | HTML со списком проблем по категориям (включая недоступность SUNAPI и аппаратные события) |
| История | Журнал смены статусов регистраторов и каналов в SQLite |

Результаты опроса: метрики и история → SQLite; `last_status` / `last_check_at` → конфиг.

## Представление для пользователя

Основные экраны отражают бизнес-задачи, а не техническую структуру кода:

- **Объекты** — группы регистраторов по `object_name`, сводные дашборды исправности и времени, экспорт ошибок.
- **Регистраторы** — плоский список с теми же дашбордами.
- **Каналы** — детализация по камерам с фильтрацией.
- **Время** — фокус на NTP и расхождении часов; массовое исправление.
- **Статус** — дашборд по категориям здоровья (температура, диски, архив и т.д.).
- **Настройки** — credentials и пороги.
- **История** — хронология изменений статусов.

Поиск и сортировка (по имени / по статусу) работают на уровне объектов и регистраторов. Проблемные объекты поднимаются выше за счёт сортировки по severity.

## Ограничения и допущения

- Оборудование — Wisenet/Hanwha; опрос только через SUNAPI (HTTP/HTTPS).
- Единые credentials для всего парка; пароли не должны попадать в публичный репозиторий.
- Автоперезагрузка устройств, создание тикетов, ML-анализ кадров, SNMP/PoE — не реализованы; заложены в дорожной карте (этапы 2–5).
- Критичные зоны (касса, хранилище) с повышенным приоритетом — будущая функция после инвентаризации зон.
- Масштаб: архитектура рассчитана на рост до тысяч камер через модель «регистратор → каналы»; при массовых отказах на объекте проблемы группируются по `object_name`.
